= Migrating to the eventuate-common split
:toc:

eventuate-common is split into seven repositories.
Each one publishes its modules under its own group, with its own version properties.
Some packages are renamed, and the database and ZooKeeper images get their own Docker Compose variables.

The split is a clean break.
The old packages and the `io.eventuate.common` coordinates are not kept, even deprecated.
eventuate-common itself is not changed, so a consumer that has not been migrated keeps building against `0.23.0.BUILD-SNAPSHOT` of eventuate-common.

The recipe `io.eventuate.common.split.MigrateToEventuateCommonSplit`, in `rewrite.yml` in this directory, makes the changes described below.

The Quarkus platform repositories, such as `eventuate-common-quarkus`, and the Quarkus and Micronaut example projects are not migrated yet.
They stay on eventuate-common.

== Running the recipe

Clone this repository and set `OPENREWRITE_DIR` to its directory.
Then run the recipe from the consumer's root directory:

[source,sh]
----
$OPENREWRITE_DIR/_run-rewrite-recipe.sh \
    --init-script $OPENREWRITE_DIR/eventuate-common-split/rewrite-init.gradle \
    --config-file $OPENREWRITE_DIR/eventuate-common-split/rewrite.yml \
    --recipe io.eventuate.common.split.MigrateToEventuateCommonSplit
----

The script applies the OpenRewrite Gradle plugin with an init script, so the consumer's build files don't change to run it.
It writes Gradle's output to a log file in `/var/tmp`.

`rewrite-init.gradle` is needed when the consumer's dependencies, such as `eventuate-common-messaging`, have already been migrated.
Without it, Gradle fails with a capability conflict between the old and new modules, or the consumer fails to compile, before the recipe runs.

The recipe does not change `gradle.properties`.
After it runs:

. Add to `gradle.properties` each version property, listed below, that the build files now use.
. Remove `eventuateCommonVersion` and `eventuateCommonImageVersion`.
. Build the consumer, for example with `./gradlew testClasses`.

Running the recipe a second time changes nothing.

== What changes

A consumer changes in five places:

* *Dependencies.* Each dependency on an `io.eventuate.common:<module>:${eventuateCommonVersion}` artifact changes to the group and version property of the repository that now publishes the module.
  The module names do not change.
* *BOM imports.* A `build.gradle` that imports `io.eventuate.common:eventuate-common-bom` as a platform imports the seven new BOMs instead.
* *Packages.* The packages in the tables below are renamed.
* *Testcontainers.* The database containers and `EventuateZookeeperContainer` move out of `eventuate-common-testcontainers` into new modules.
  The recipe adds a dependency on the new module to a Gradle project that uses one of the moved classes.
* *Images.* The Compose variable `EVENTUATE_COMMON_VERSION` is replaced by `EVENTUATE_COMMON_DATABASE_VERSION` for the database images and `EVENTUATE_COMMON_ZOOKEEPER_VERSION` for `eventuate-zookeeper`.

Each new module also declares the capability of its old `io.eventuate.common` coordinates in its Gradle module metadata.
A Gradle build that gets both the old and the new module, for example through a dependency that has not been migrated, fails with a capability conflict that names the two modules, instead of putting two copies of the classes on the classpath.
Maven builds do not read the capabilities.

== Version properties and Compose variables

Before the split, consumers used two Gradle properties: `eventuateCommonVersion` for the artifacts and `eventuateCommonImageVersion` for the images.
After the migration, no build file uses them.

[cols="1,1,1,1"]
|===
| Repository | Version property | Image version property | Compose variable

| `eventuate-common-id`
| `eventuateCommonIdVersion`
|
|

| `eventuate-common-json`
| `eventuateCommonJsonVersion`
|
|

| `eventuate-common-coordination-leadership`
| `eventuateCommonCoordinationLeadershipVersion`
|
|

| `eventuate-common-testcontainers`
| `eventuateCommonTestcontainersVersion`
|
|

| `eventuate-common-zookeeper`
| `eventuateCommonZookeeperVersion`
| `eventuateCommonZookeeperImageVersion`
| `EVENTUATE_COMMON_ZOOKEEPER_VERSION`

| `eventuate-common-database`
| `eventuateCommonDatabaseVersion`
| `eventuateCommonDatabaseImageVersion`
| `EVENTUATE_COMMON_DATABASE_VERSION`

| `eventuate-common-eventuate-local`
| `eventuateCommonEventuateLocalVersion`
|
|
|===

The image names do not change.
Their tags follow the version of the repository that builds them, which continues eventuate-common's versions, such as `eventuate-mysql8:0.23.0.BUILD-SNAPSHOT`.

In the Compose files, the recipe changes `${EVENTUATE_COMMON_VERSION}` to `${EVENTUATE_COMMON_DATABASE_VERSION}` in the tags of the database images, and to `${EVENTUATE_COMMON_ZOOKEEPER_VERSION}` in the tag of `eventuate-zookeeper`.
In `build.gradle`, it changes

[source,groovy]
----
environment.put "EVENTUATE_COMMON_VERSION", eventuateCommonImageVersion
----

to

[source,groovy]
----
environment.put "EVENTUATE_COMMON_DATABASE_VERSION", eventuateCommonDatabaseImageVersion
environment.put "EVENTUATE_COMMON_ZOOKEEPER_VERSION", eventuateCommonZookeeperImageVersion
----

Check any other place that sets `EVENTUATE_COMMON_VERSION`, such as a shell script or a CircleCI config, by hand: the recipe changes only `build.gradle` and `docker-compose*.yml` files.
